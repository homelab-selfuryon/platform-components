# Onboarding a team

A file `teams/<name>.cue` is the whole onboarding:

```cue
package teams

Teams: notes: {
	quota: {
		staging: {requestsCPU: "2", requestsMemory: "2Gi", limitsMemory: "4Gi", pods: "20"}
		prod:    {requestsCPU: "4", requestsMemory: "4Gi", limitsMemory: "8Gi", pods: "30"}
		preview: {requestsCPU: "500m", requestsMemory: "512Mi", limitsMemory: "1Gi", pods: "8"}
	}
}
```

It renders a component `team-<name>` in the `tenants` set. The matching GitHub team and the
repositories are created in `platform-terraform/github`; the apps register in `gitops`
(`apps/<team>/<app>/app.cue`).

## What the team gets

| Object                                       | Where                                 | Purpose                                                                                                                                               |
| -------------------------------------------- | ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Namespaces `<team>-staging`, `<team>-prod`   | cluster                               | Pod Security `restricted`, labels `homelab-selfuryon.github.io/team` and `/env` (admission and the Gateways select on them)                           |
| ResourceQuota `team-quota`                   | each namespace                        | from the team file                                                                                                                                    |
| Default-deny CiliumNetworkPolicy, LimitRange | each namespace (generated by Kyverno) | apps open what they need in their own policy                                                                                                          |
| ServiceAccount `deployer`, Role `deployer`   | each namespace                        | what Argo CD syncs as: the kinds `#Service` renders (teams/component.cue, `#DeployKinds`), no Secrets, no RBAC objects, no pods/exec                  |
| RoleBinding `team-view`                      | each namespace                        | the GitHub team's group: `view` (no Secrets)                                                                                                          |
| AppProject `<team>`                          | `argocd-system`                       | sources `oci://ghcr.io/homelab-selfuryon/<team>-*`, destinations the two namespaces, no cluster resources, `destinationServiceAccounts` -> `deployer` |
| AppProject `<team>-preview`                  | `argocd-system`                       | the same sources, destinations `<team>-pr-*`, only the `Namespace` cluster resource                                                                   |

The Flux ServiceAccount of the component (`component-team-<name>`) may create exactly these: the
whitelist lists the two namespaces and the preview ClusterRole by name, and admission holds the
ServiceAccount to the team's namespaces and `argocd-system`.

## Preview environments

Preview namespaces `<team>-pr-<n>` do not exist ahead of time: the ApplicationSet in `gitops` (pull
request generator) makes Argo CD create them, with the labels `team=<team>` and `env=preview`
(`managedNamespaceMetadata`). Design:

1. Argo syncs preview applications as `argocd-system/<team>-preview-deployer`
   (`destinationServiceAccounts[].defaultServiceAccount: argocd-system:<team>-preview-deployer`). That
   ServiceAccount lives in a fixed namespace, so one ClusterRoleBinding can name it; its
   ClusterRole has the `deployer` rules plus `namespaces`.
2. Cluster-wide rights for a ServiceAccount are far too much for RBAC alone, so Kyverno holds it:
   policy `preview-deployer-scope` denies any create, update or delete by that ServiceAccount
   unless the object's namespace (or, for a `Namespace`, its name) matches `^<team>-pr-[0-9]+$`.
3. A namespace named `<team>-pr-<n>` must carry the team label and `env=preview` and enforce
   Pod Security `restricted` (policy `tenant-namespace-labels`); once it does, admission
   generates its default-deny policy, LimitRange and the team's preview quota and requires
   images signed by `app-preview.yaml` (never accepted in staging or prod).
4. The team cannot widen any of this: the AppProject only allows destinations `<team>-pr-*`, the
   ServiceAccount, ClusterRole and the policies are platform-owned (CODEOWNERS), and the
   `deployer` of a long-lived namespace cannot touch RBAC objects.

Argo CD may impersonate only the ServiceAccounts named in the application controller's ClusterRole
(`deployer`, `<team>-preview-deployer`).
